# v4.00 Overview — Live Service & Content Pipeline Scalability

## Version Purpose

Make Tiny Factory sustainable for one developer to operate, balance, debug, migrate, and expand safely.

## Primary Validation Question

> **Can one developer efficiently operate and expand Tiny Factory over the long term?**

## Scalability Objective

Lower the cost and risk of adding machines, events, balance changes, progression content, and schema changes.

## Player-Facing Objective

Players receive:

- more reliable updates
- safer balance changes
- limited-time content where appropriate
- fewer broken migrations
- more consistent event quality

## Architecture Objective

Add:

- data-driven definitions
- validators
- simulation tests
- feature flags
- constrained remote configuration
- migration tools
- rollback-safe operational patterns
- debugging/admin tools
- economy/performance observability

## Planned Phases

1. Data-Driven Content Pipeline
2. Developer Tools & Automated Validation
3. Feature Flags & Live Configuration
4. Data Reliability, Migrations & Observability
5. Seasonal Content Pilot & Operations Validation

## Economy Considerations

Live changes must be auditable and bounded. Do not create remote configuration that can silently invalidate player holdings.

## Security Risks

- privileged admin actions
- unsafe live configuration
- feature-flag leakage
- migration mistakes
- event reward exploits

## Performance Risks

- analytics overhead
- debug instrumentation left enabled
- content validation cost at runtime
- event-specific simulation spikes

## Deferred Systems

Future large-scale worlds, markets, clans, scripting, and mega-factories remain conditional.

## Exit Criteria

- adding standard machine content is low-risk
- invalid content is caught before release
- migrations can be tested and observed
- feature rollout can be controlled
- event content can be enabled/disabled safely
- developer tools reduce diagnosis time
- a seasonal pilot runs without destabilizing the core game
